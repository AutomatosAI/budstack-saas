THE ROBOTS.TXT RULE THAT SHAPED THE DESIGN. A crawler that matches its own
`User-agent` group uses THAT group and ignores the `*` group entirely (RFC 9309
§2.2.1). So a blocked bot gets its own group with `Disallow: /` (complete on its
own — the admin paths need no repeating), and an ALLOWED bot gets no group at
all. Publishing `User-agent: GPTBot` / `Allow: /` to "be explicit" would have
taken GPTBot out of the wildcard group and handed it `/api/`, `/tenant-admin/`
and `/auth/`. Hence 'open' renders comments and nothing functional — asserted
(`userAgents(txt)` is exactly `["*"]` under 'open').

TWO PARSERS, TWO DIRECTIONS, ON PURPOSE. The PLAN fails closed ('basic' — a DB
blip must not hand out Pro); the POLICY fails open ('open' — an unreadable
settings blob must never be read as "this store asked to be hidden from AI
answers"). Both directions are table-tested.

BYTE-IDENTICAL FOR BASIC. The pre-story file is frozen as a literal in the test
(not derived from the renderer, which would make the assertion tautological) and

NO xAI ROW SHIPS — an evidenced deviation from the story's AC, stated here
rather than papered over. The AC asks for "xAI search UA". xAI publishes no
crawler user-agent token: x.ai's own robots.txt names other operators' bots and
not its own (curled 2026-08-14), and Cloudflare's AI Crawl Control bot reference
lists no xAI crawler. Third-party directories disagree with each other between
`GrokBot`, `xAI-Grok` and `xAI-Crawler`. Emitting a guessed token would tell an
owner they had blocked something they had not — the one failure this feature
cannot have. The registry is data; the row is one line the day xAI documents it.
Tokens that DID ship were verified against primary sources on 2026-08-14:

THIS ONE 404s, WHICH IS THE OPPOSITE OF EVERY OTHER STOREFRONT SURFACE. The
run's contract is that the storefront DEGRADES on plan and never blocks — a
shopper must not meet a paywall. Nothing shops here. The file is a Pro
deliverable addressed to a machine, and a Basic store does not publish one; an
empty 200 would be a CLAIM ("this store has nothing to show you") and the claim
is false. So the route reads the plan through the same `isSeoProUnlocked` the
robots.txt beside it uses, and 404s before it runs a single query — asserted:
all three `findMany` mocks uncalled on a Basic request. Fail-closed on an
unreadable plan for the recoverable reason: a store that should publish gets it
back next request; a file a crawler has already read cannot be taken back.

IT HONOURS BOTH EXCLUSIONS, WHICH THE SITEMAP DELIBERATELY DOES NOT. The parent
kept `sitemapExclude` and `robots.noindex` independent on purpose (US-023's
audit exists to REPORT the disagreement, so forcing them together would hide the
state it looks for). llms.txt honours both, because a document whose entire
purpose is "here is my store, please read it" cannot advertise a URL whose own
page asks not to be read. That needed one new predicate — `isEntityNoindexed` in
`lib/seo/indexing.ts`, mirroring `isSitemapExcluded`'s signature (plan as a
resolved boolean: one document asks the question once per row, and the plan
cannot change between two rows of one render). `nofollow` is NOT consulted — it
is a statement about the links on a page, not about the page. The sitemap is
unchanged.

NO SILENT TRUNCATION. Products and posts render a BUDGET (100 / 50) so a store
with thousands of rows publishes something a model will actually read. The
budget is applied at RENDER, never as a `take` — a query-level cap would hide
the count from the builder, and a shortened inventory that cannot say it was
shortened reads as a complete one. Every section therefore opens with its own
index URL, the identity block names the sitemap (which stays exhaustive), and an
over-budget section prints "100 of 137 listed above. The complete list is at …".
The count is of PUBLISHABLE rows, not fetched ones: an excluded row was never
going to be listed, and counting it would report a number the owner cannot
reconcile with their catalogue.

MARKDOWN IS AN INJECTION SURFACE TOO. Not a script one — the file is served as
text/plain — but a correctness one: a product called `Blue Dream [Reserve]`
closes its own link and renders the rest as prose, and a condition slug
containing a parenthesis terminates the URL early (`storeCanonical`
percent-encodes what `new URL` does, and parentheses are not on that list). Both
values are owner-typed. `escapeMarkdownText` escapes `\ [ ]` and collapses
whitespace (body copy pasted into a title field would otherwise split the list
item in two); `escapeMarkdownUrl` percent-encodes parentheses, which resolves to
the identical URL.

REUSE, NOT A SECOND OPINION. Every URL comes from `storeCanonical` over
`productPath` / `conditionPath` / `wirePostPath` — the same builders the pages'
canonicals and the sitemap use, so a link here and the canonical of the page it
points at cannot disagree. Row descriptions use the precedence the metadata
builders already apply (`seo.description` -> truncated body copy), so the
sentence a model reads is the sentence the page publishes. The address goes
through `buildPostalAddress`: its completeness floor (street + locality +
country) decides whether a line is emitted at all, so this file cannot assert an
address the JSON-LD refuses to state. The store summary is authored-home-
description -> tagline -> the homepage's own fallback sentence, all off the row
`getCurrentTenant` already resolved — no extra query, and the query shape
mirrors the sitemap route beside it (tenantId named in every `where`, bound in
`runWithTenantContextAsync`, `deletedAt: null` and `drGreenStrainId NOT NULL`
stated where a reader can see them).

"TOP" AND "RECENT" ARE THE STORE'S OWN ORDERS, NOT INVENTED ONES. Products sort
by `displayOrder` then `name` (the owner's arrangement, with the column's
`@default(0)` ties broken stably, so the budget cuts a stable list). Posts sort
`createdAt: desc` — the exact order the Wire index renders — so "recent posts"
means the posts a visitor sees at the top of that page. Conditions are NOT
budgeted: a store's guides are the whole GEO wedge this PRD is built on.

THE COPY IS THE ACCEPTANCE CRITERION. The card states, in the same breath as the
feature: llms.txt is a proposed standard no AI company has committed to reading,
~10% of sites publish one, the largest study of it (SE Ranking, 300,000 domains)
found no measurable change in AI citations, and the actual case for shipping is
that it costs nothing. The copy lives in constants so the four claims are

would reach for ("guarantee", "boost", "rank higher", "more traffic"). The card

THE AC (d) SUBSTITUTION — READ THIS BEFORE "FIXING" auditWireVisibility.
The AC specifies "a tenant whose blog surface is the Automatos Shadow-DOM widget
(wireMode column)". That premise is false against this repo, verified three ways
on 2026-08-14:
  * `tenants.wireMode` is MANUAL|ASSISTED and its own schema comment says what
    it is — "The Wire authoring mode ... (Automatos pushes drafts)"
    (prisma/schema.prisma:821). It selects who WRITES a post. ASSISTED drafts
    land as ordinary `posts` rows for review
    (app/api/integrations/automatos/posts/route.ts:114) and publish through the
    same path as a hand-written one. ASSISTED is if anything BETTER for
    crawlability, not worse.
  * The Wire's storefront surfaces are ordinary server-rendered Next routes
    (app/store/[slug]/the-wire/page.tsx, [postSlug]/page.tsx, revalidate 60) —
    the post body is sanitized HTML in the response. Fully crawlable.
  * The Automatos widget IS Shadow-DOM (`attachShadow({mode:"open"})`,
    public/automatos-widget.js:5) but it is initialised as `widget: "chat"`
    (components/admin/AutomatosWidgetWrapper.tsx:28) — a chat FAB. It renders no
    blog content anywhere. There is no template section that fetches posts
    client-side either: `BlogFeed` takes them as props.
So the specified check could never fire on any tenant: it would be dead code
asserting something false about the platform. What DOES make Wire content
invisible to every crawler and LLM is the ordinary case ASSISTED mode produces
at volume — a draft has no page. `published: false` is the real invisibility,
the mode is why a store accumulates it without noticing (named in the message
only when it is on, and named as the explanation, never as the fault), and The

THE SPIKE, BECAUSE AC 4 TURNS ON IT. Re-fetched the published OpenAPI document
(api.automatos.app/openapi.json, HTTP 200, 664 paths) rather than trusting the
parent story's summary, and the two facts that decided the design are:
  * `WidgetChatRequest.model_id` IS on the wire — optional string, exactly as
    the shipped browser SDK sends it (`public/automatos-widget.js` passes
    `model_id: this.config.modelId`). So per-model rows are POSSIBLE.
  * There is NO model-listing endpoint under `/api/widgets/*`. `/api/models/`
    exists but authenticates as a platform USER, which the parent spike already
    established a tenant's widget key cannot reach. The ONLY workspace-scoped
    discovery surface a widget key opens is `GET /api/widgets/config`, whose
    documented response is `{workspace_id, config}` with `config` declared
    `additionalProperties: true` AND NO DECLARED KEYS.
  So the spec permits variation but does not promise a list to vary across, and
  no live key exists on this machine to discover one. `requestAutomatosWidgetModels`
  therefore reads OPTIMISTICALLY AND FAILS TO NOTHING: three plausible key names
  (`models` / `enabled_models` / `available_models`), entries as strings or as
  objects carrying an id, and ANY other shape — including the likely one, a
  config with no models in it — returns []. An empty list is not an error; it is
  AC 4's specified fallback, and the run asks the agent's default model as a
  single engine labelled `workspace-default`. That label is not a vendor name,
  which is the rule: every other label is a model id the workspace itself
  returned.
