WHAT LANDED
- lib/seo/store-metadata.ts (new): buildStoreMetadata(), a PURE builder for the
  layout-level Metadata. Pure because generateMetadata runs in a render path with
  no error.tsx above it — a throw there is a blank page, so every input (Json

  (the favicon source), i.e. one more nested join on a query the layout already
  makes, not a new round trip.

  image ref (bare S3 key / path / absolute URL / presigned URL) to a durable,
  origin-relative /api/public/images/ path, or null. Fails CLOSED, which is what
  keeps presigned URLs out of SEO-visible tags (PROMPT anti-pattern).

14.2.35 — not assumed):

  `i < metadataItems.length - 2`, and app/store/[slug]/layout.tsx sits at exactly
  length-2 for app/store/[slug]/page.tsx. => THE HOMEPAGE TITLE IS NOT WRAPPED.
  Its existing "{businessName} - Medical Cannabis Solutions" renders verbatim, so
  page.tsx:358-418 needed no edit and is not regressed. /products, /the-wire/...

  no page-specific value is hardcoded at layout level.
- Deliberately NOT set at layout level: og:url and alternates.canonical. A store-
  root URL on a product page is a worse tag than none; US-007 emits them per page.

THE faq KEY — remapped, not retired-and-forgotten
/faq has redirected to /support since app/store/[slug]/faq/page.tsx:4-5, so any
FAQ metadata an owner wrote describes the page a visitor actually lands on.
Handling: `faq` is out of STORE_SEO_PAGE_KEYS (the enum now 400s it) but lives
in LEGACY_STORE_SEO_PAGE_KEYS, so readStorePageSeo(pageSeo, "support") falls
back to it — whole entry, never a field-by-field blend of two records nobody
authored. dropLegacyStorePageSeoKeys retires the row the first time an owner
saves /support, on BOTH the route and the client's optimistic state; without
that, clearing /support would resurrect the old FAQ copy as live metadata while
the admin badge read "Default".

HOW NEXT MERGES THIS (read from next/dist/lib/metadata/resolve-metadata.js,
14.2.35 — the US-001 claims re-verified, plus what US-002 needed):
- collectMetadata pushes an item for EVERY tree node, layout-less ones included
  (resolve-metadata.js:295-332). /store/[slug]/about is 5 items (root, store,
  [slug] layout, about, __PAGE__), so the layout sits at i=2 < length-2=3 and
  its title.template IS stashed → a plain-string page title renders
  "About Us | Acme". The homepage is 4 items, layout at exactly length-2 → not
  templated, which is why US-001 could leave page.tsx alone.
- Therefore an AUTHORED title is emitted as `{absolute}`: the SEO Manager shows
  the owner a Google preview of the exact string they typed, and suffixing it
  would make that preview a lie. DEFAULTS are plain strings, so they get the
  brand suffix.
- openGraph is REPLACED, never merged (:146), so the page re-declares
  siteName/type/locale — omitting them would strip og:site_name from exactly
  the pages this story fixes. og/twitter TITLES are deliberately left unset:
  postProcessMetadata (:406-445) fills them from the RESOLVED title (after the
  template), which is the only way og:title and <title> are guaranteed equal.
- metadataBase is inherited by children (:130 — source.metadataBase ?? target's),
  so a relative og:image from the public-image route absolutises against the
  layout's base. og:image dimensions are NOT declared: the value is a URL the
  owner pasted, and 1200x630 we have not measured makes scrapers crop wrong
  (US-018's generated images can declare them).
- og:image reuses storedPublicImagePath, so a presigned S3 URL left over from
  before Email US-005 is DROPPED rather than rendered as a tag that 403s an
  hour later.
