WHAT LANDED
- prisma/schema.prisma: new `platform_posts` model, placed beside
  learning_resources (the other non-tenant-scoped platform table) rather than in
  the tenant block, so the grouping states the scoping intent.
  Fields: id uuid / slug @unique / title / excerpt? / content / coverImage? /
  coverImageAlt? / authorName / authorRole? / published(false) / publishedAt? /
  seo Json? / createdAt / updatedAt.
- prisma/migrations/20260815000000_add_platform_posts/migration.sql — a TIMESTAMPED
  DIRECTORY, so entrypoint.sh's `prisma migrate deploy` actually applies it.
- tests/unit/platform-posts-schema.test.ts — 9 offline guards (see below).

DECISIONS
- authorName/authorRole are denormalised strings with NO relation and no @relation
  anywhere in the model, per AC. Two independent reasons, both now in the schema
  comment: `users` is itself in tenantScopedModels so an FK join is unreadable from
  the apex, and getCurrentUser().id is a CLERK id — writing it into a uuid FK is the
  P2003 that broke the lekkerweed blog in #226. learning_resources sets the
  precedent of a platform table with no author relation.
- NULLABILITY: title/content/slug/authorName are required; excerpt, coverImage,
  coverImageAlt, authorRole, publishedAt, seo are nullable. Mirrors tenant `posts`
  (excerpt?/coverImage? optional, author required). A draft is
  (published=false, publishedAt NULL); publishedAt is meant to be set once at first
  publish so the public date does not jump on later typo fixes — US-004 owns
  enforcing that.
- INDEX DEVIATION, called out deliberately: the AC asks for "indexes on
  [published, publishedAt] and [slug]". I shipped @@index([published, publishedAt])
  plus the UNIQUE index that `slug @unique` already creates
  (platform_posts_slug_key). I did NOT add a second plain @@index([slug]) — it would
  be redundant storage and write cost serving the identical lookup. Slug lookups
  (/blog/[slug], the editor's uniqueness check) are indexed. platform_leads does
  exactly this: `email @unique` with no extra index beside it. Flagging it so a
  reviewer sees a decision, not an omission.

THE ALLOWLISTS ARE UNCHANGED — PROVEN, NOT ASSERTED
Rather than eyeball the copy, I stood up a throwaway parity harness: the ORIGINAL
inline config pasted verbatim from git HEAD alongside the real shipped module,
both run over a 25-input corpus (hostile + benign: script tags, on* handlers,
javascript:/data:/ftp: URLs, an unclosed-tag soup, svg+script, the two allowed
iframe hosts, a lookalike host, a protocol-relative iframe src, style attributes
that the allowedStyles map would have permitted, form/object/embed). All 25
produced byte-identical output, and the harness carried a non-vacuity assertion
so a silently empty corpus could not pass. The harness was then DELETED — it
contains a second copy of the config, which is the exact thing this story exists
to remove.

FOUND: allowedStyles IS INERT TODAY (carried over anyway, deliberately)
The attribute map is `'*': ['class','id']` with the original author's comment
"Removed 'style' from global allowlist", and no per-tag list re-admits `style`.
sanitize-html only consults `allowedStyles` for a style attribute that survived
`allowedAttributes`, so every inline style is dropped outright and the whole
regex map is dead config. It was copied over unchanged regardless: the AC says
copy exactly and loosen nothing, and admitting `style` to make the map live
would be a loosening. Documented in the file so the next reader does not mistake
the map for evidence that inline styles are permitted.
