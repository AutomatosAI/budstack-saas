THE SLUG REGEX IS ENFORCED SERVER-SIDE (the tenant gap, closed)
POST_SLUG_PATTERN and POST_SLUG_MAX_LENGTH are applied in the Zod schema, not

underscores, digits and a leading hyphen — POST_SLUG_PATTERN has to take those
because the editor posts stored legacy slugs straight back.

FOUND: A PUNCTUATION TITLE DERIVES THE SLUG "-", WHICH IS VALID
slugifyPostTitle("!!! ??? ***") returns a bare "-": the ! ? * are stripped as
non-word, the space-hyphens survive, and the run collapses to one. That PASSES
POST_SLUG_PATTERN — it must, see above — so a title of punctuation alone would
have published at /blog/-. resolveCreateSlug is therefore stricter than the
validator, and only on the DERIVED path: a derived slug must carry at least one
[a-z0-9], and one longer than POST_SLUG_MAX_LENGTH (reachable — the title cap is
300) is refused rather than truncated. Either way the answer is "enter a slug
explicitly", never a URL nobody chose. An AUTHORED slug is still taken verbatim.
Three cases pinned.

PUBLISHED SLUGS ARE LOCKED — this is the run's anti-pattern list, in code
PATCH refuses a slug change on a published post with 409 and a message that says
why. It is enforced in the API, not only in the editor US-007 will build, so an
API caller cannot route around the form's warning. US-019 (auto-301) is what
lifts this: search PUBLISHED_SLUG_LOCKED_MESSAGE in lib/platform/posts.ts. A
live post re-sending its OWN slug is not a rename and is allowed (the editor
posts the slug on every save); a draft renames freely.

publishedAt SEMANTICS, ALL FIVE PINNED
create published -> stamped now; create draft -> null; draft->published ->
stamped; edit while live -> the ORIGINAL date, unchanged; unpublish -> the
original date KEPT, not cleared. The last one is a judgement call the schema
comment does not settle: clearing it would make a re-publish invent a new date,
which contradicts "stamped once". An edit that says nothing about publishing
writes neither column.

DUPLICATE SLUG -> 409, TWICE OVER
findUnique pre-check for the clean message (the slug is named in it), plus a
P2002 catch for the race between that read and the insert, mapping to the same
409. No Prisma text reaches the client. PATCH additionally maps P2025 to 404,
and DELETE maps P2025 to 404 rather than reporting success on a row that was
not there.

THE DECISION THAT MATTERED — publicUrl has to be DURABLE
The tenant Wire form stores `data.publicUrl || data.url` (post-form.tsx:100),
and `url` is a presigned link that dies in ~1h. So a platform route that only
returned the presigned URL would satisfy "same response shape" on paper and
store a blog cover that breaks the same afternoon — the exact failure the
tenant route's own comment describes. The durable path is /api/public/images/,
and its parser only served `tenants/{id}/uploads/`, so it had to learn one more
shape. That is why this story touched a shared module and not just the route.

Two alternatives rejected:
- Uploading under `tenants/platform/uploads/` to avoid touching the module. It
  works mechanically (the S3 scope guard would accept it), and that is the
  problem: a fabricated tenant id that satisfies a tenant guard by accident,
  written into every key, for the rest of the bucket's life.
- Returning publicUrl: null and letting US-007 deal with it. That pushes an
  expiring URL into the database, which is what the whole durable-image route
  exists to prevent.

Scope of the widening, checked rather than assumed: the platform prefix opens
`platform/uploads/` ONLY. The pre-existing platform branding keys written by
super-admin/platform-settings (`platform/logo-*`, `platform/favicon-*`) are
passed to uploadFile as a FILENAME with no prefix, so they land at
`{folderPrefix}uploads/{ts}-platform/logo-…` and match neither shape — they
stay private. Four negative tests pin that (`platform/logo-…`,
`platform/backups/…`, `platformX/uploads/…`, an SVG under the platform prefix).
PublicImageRequest.tenantId is now `string | null`; both call sites (the images
route, the OG card route) read only s3Key and contentType, so nothing broke.

WHY NOT /api/tenant-admin/upload (AC-2, verified in code)
It is withTenantAuth, which reads tenantId off the user and 403s when there is
none — a super-admin has none. Under impersonation it would succeed and file
the platform's blog cover inside a tenant's folder, where a tenant delete would
eventually take it. Also: getFileUrl is called WITHOUT the { tenantId } option
here, deliberately — that option asserts the key sits in that tenant's prefix
and would throw 403 on every platform upload. A test pins the bare call.

[2026-08-16] US-019 PASS — Slug changes issue a 301

WHAT LANDED
- New model `platform_seo_redirects` + timestamped migration
  20260816030000_add_platform_seo_redirects. Kept OUT of `tenantScopedModels`,
  like every other platform_* table.
- Why a SECOND table rather than platform rows in `seo_redirects`: that table's
  tenantId is NOT NULL with an FK to tenants AND the model is in
  tenantScopedModels, so a null-tenant row would be filtered out of every read by
  the $extends rewrite and would NOT be deduplicated by
  @@unique([tenantId, fromPath]) — Postgres treats NULLs in a unique index as
  distinct, so two rows could claim the same path.
- Everything ELSE is reused, not rewritten. `planSlugRenameRedirect`
  (lib/seo/slug-redirects.ts) is pure and decides all three steps unchanged, so
  chains COLLAPSE rather than nest and a rename-back clears the rule that would
  otherwise shadow the post's new address. lib/seo/platform-slug-redirects.ts is
  ~60 lines: the same plan, applied to the other table, with no tenantId in any
  predicate.
- Middleware fires it. The apex previously had NO redirect scope at all
  (`storeRedirectScope` returns null for a null hint), so `resolvePlatformRedirect`
  was added beside `resolveStoreRedirect` — same in-memory SWR cache, same
  matcher, distinct cache key. A tenant request costs two string comparisons and
  never fetches.
- The feed (`/api/public/seo/redirects`) grew ONE query parameter, `scope=platform`,
  which skips tenant resolution and the seo.pro gate — there is no tenant to
  resolve and the platform is not a customer of itself. Absent scope = today's
  behaviour, byte for byte. No new public route, so no allowlist entry needed;
  auth-public-routes.ts's reason string was extended to say what the new scope

DECISION WORTH KNOWING
A redirect is written only when `existing.publishedAt !== null`, not when

not: a post unpublished, renamed and republished still has an old URL in the
wild. A never-published draft gets no rule (nothing links to it, and a rule would
count against the table's cap).

THE DECISION THAT SHAPED THE REST: IT JUDGES WHAT THE PAGE SERVES
Every check runs over the output of the same resolvers `generateMetadata` calls,
so the audit cannot drift from the tags it describes. That needed two small
extractions, both behaviour-preserving:
  - `resolvePlatformPageSeo` out of `buildPlatformPageMetadata`
  - `resolvePlatformPostSeo` out of `buildPlatformPostMetadata`
Each returns the resolved strings plus whether the field fell through to the
platform default — a question a built `Metadata` cannot answer (its
openGraph.images is a five-way union, and "this is the default title" is not
recoverable from the string without restating the cascade). The builders now
consume their own resolver; nothing else about them changed.
Third extraction, same reason: the guide fallback `{title, description}` was two
literals inside app/documents/[slug]/page.tsx. It is now `platformGuideFallback`
in lib/platform/seo-routes.ts, called by the page AND the audit, so the audit
cannot report a title the page does not serve.

TWO JUDGEMENT CALLS WORTH REVIEWING
1. `og-image-missing` compares the RENDERED CARD, not the column. The US-013 seed
   pointed all 15 static routes AT the platform hero, so judging "is the column
   filled in" would call fifteen identical grey cards fifteen images of their
   own. Consequence: on day one the panel reports ~33 og findings (every route)
   plus any post without a cover. That is true — budstacks.io has one stock
   social image — and it is an `info` check, capped at 5 points, sorted last.
2. `title-missing` is about AUTHORSHIP, not string comparison. An authored title
   that repeats the platform default counts as the route's own. Consequence: the
   HOMEPAGE is flagged, because PLATFORM_ROUTE_FALLBACKS["/"] is {} and it
   inherits the layout's title. The advice is still right — the site's most
   valuable string is currently a shared constant — but it is worth knowing the
   first thing the panel will say about `/` is "no title of its own", alongside
   /blog and /contact, which is the state the US-015 header predicted.

THE CANONICAL CHECK IS NOT A TAUTOLOGY
It parses the declared canonical and asks whether its path names THIS page,
rather than comparing the resolver's output with itself. That catches the real
failure: `platformCanonical` returns the bare origin when `new URL` cannot parse
a path, so an unparseable route would declare the HOMEPAGE canonical and ask
Google to index that instead. Trailing slashes and percent-encoding are
normalised on both sides. Today every route and post passes it; it is a guard,
and it is the only check here that can fail on data nobody typed.
