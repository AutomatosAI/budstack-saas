WHAT WAS FOUND (decision-level)
- US-001 LEFT A LIVE DOUBLE SUFFIX, now fixed. The article page built its own
  `"{post.title} | {businessName}"` title, and US-001's layout stashes a
  "%s | {businessName}" template for every segment below the homepage. An
  article sits at metadataItems i=2 with length=6 (root, store, [slug] layout,
  the-wire, [postSlug], __PAGE__ — collectMetadata pushes layout-less nodes
  too), so 2 < length-2=4 and the template applied: every Wire post has been
  rendering "Terpenes explained | Acme | Acme" since f81a2e6. Titles are handed
  over unsuffixed now and there is a named regression test.
- DESCRIPTION IS OMITTED, NOT undefined, when there is neither an authored one
  nor an excerpt. mergeMetadata assigns `target[key] = source[key] || null` for
  that field (resolve-metadata.js:194-205), and `for (const key_ in source)`
  walks own keys INCLUDING undefined ones — so `description: undefined` would
  NULL the layout's description instead of inheriting it. No invented third
  tier: a per-store fallback sentence would put the same description on every
  article, which is the duplicate-content defect this workstream is removing.
- twitter is declared for the CARD TYPE ONLY. postProcessMetadata (:406-442)
  fills twitter title/description/images from the resolved openGraph/metadata,
  which is the only way the card and the page cannot disagree; declaring
  images here would freeze them out of that.
- findFirst WITH FLAT FIELDS, not findUnique on slug_tenantId. `posts` is
  tenant-scoped in lib/db.ts:67, and the extension rewrites findUnique->findFirst
  while injecting tenantId — findFirst rejects a compound key
  (PrismaClientValidationError). Both call sites in this file used the compound
  form; the repo already documents the trap at api/tenant-admin/posts/route.ts:56.
- The loader binds runWithTenantContextAsync. generateMetadata resolves OUTSIDE
  the layout's context scope, so a tenant-scoped read there is an implicit
  unbound query: it warns on security.tenant_context_missing today and would
  THROW under TENANT_CONTEXT_STRICT — inside metadata, where a throw is a blank
  page (no error.tsx above it). Same pattern as
  app/tenant-admin/emails/campaigns/[id]/page.tsx:56. The explicit tenantId in
  the where is what makes the query correct; the binding makes it legal.
- `published: true` moved INTO the query (it was a check on the result). An
  unpublished draft's title can no longer reach the 404 page's <title>:
  metadata resolves before the body calls notFound().
- WirePost row type is stated explicitly. The any-widened prisma export
  collapses a generic's inferred T to `{}` through runWithTenantContextAsync<T>
  — 14 TS2339s until the type was named (the #229-class repo trap, one layer on).
- og:image passes through storedPublicImagePath, never re-signed: a presigned S3
  URL left over from before Email US-005 is DROPPED (it 403s an hour later and
  the tag looks correct). An unusable authored ogImage falls through to the
  cover image rather than emitting nothing.
- createdAt is parsed defensively (Date OR string OR neither). A JSON round trip
  turns the Date into a string and `new Date("nonsense").toISOString()` throws
  RangeError — the #229 failure class, in a path with no error boundary.
- The index page is NOT in STORE_SEO_PAGE_KEYS. The PRD allows "pageSeo key or
  sensible default" (tasks/prd-seo-supercharge.md:59); the default keeps the SEO
  Manager tab and the write-route enum untouched. Making it authorable later is
  one entry in store-pages.ts plus the delegator swap.
