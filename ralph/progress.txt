THE SLUG REGEX IS ENFORCED SERVER-SIDE (the tenant gap, closed)
POST_SLUG_PATTERN and POST_SLUG_MAX_LENGTH are applied in the Zod schema, not

because the editor posts stored legacy slugs straight back.

FOUND: A PUNCTUATION TITLE DERIVES THE SLUG "-", WHICH IS VALID
slugifyPostTitle("!!! ??? ***") returns a bare "-": the ! ? * are stripped as
non-word, the space-hyphens survive, and the run collapses to one. That PASSES
POST_SLUG_PATTERN — it must, see above — so a title of punctuation alone would
have published at /blog/-. resolveCreateSlug is therefore stricter than the
validator, and only on the DERIVED path: a derived slug must carry at least one
[a-z0-9], and one longer than POST_SLUG_MAX_LENGTH (reachable — the title cap is
300) is refused rather than truncated. Either way the answer is "enter a slug
explicitly", never a URL nobody chose. An AUTHORED slug is still taken verbatim.
Three cases pinned.

PUBLISHED SLUGS ARE LOCKED — this is the run's anti-pattern list, in code
PATCH refuses a slug change on a published post with 409 and a message that says
why. It is enforced in the API, not only in the editor US-007 will build, so an
API caller cannot route around the form's warning. US-019 (auto-301) is what
lifts this: search PUBLISHED_SLUG_LOCKED_MESSAGE in lib/platform/posts.ts. A
live post re-sending its OWN slug is not a rename and is allowed (the editor
posts the slug on every save); a draft renames freely.

publishedAt SEMANTICS, ALL FIVE PINNED
create published -> stamped now; create draft -> null; draft->published ->
stamped; edit while live -> the ORIGINAL date, unchanged; unpublish -> the
original date KEPT, not cleared. The last one is a judgement call the schema
comment does not settle: clearing it would make a re-publish invent a new date,
which contradicts "stamped once". An edit that says nothing about publishing
writes neither column.

DUPLICATE SLUG -> 409, TWICE OVER
findUnique pre-check for the clean message (the slug is named in it), plus a
P2002 catch for the race between that read and the insert, mapping to the same
409. No Prisma text reaches the client. PATCH additionally maps P2025 to 404,
and DELETE maps P2025 to 404 rather than reporting success on a row that was
not there.

THE DECISION THAT MATTERED — publicUrl has to be DURABLE
The tenant Wire form stores `data.publicUrl || data.url` (post-form.tsx:100),
and `url` is a presigned link that dies in ~1h. So a platform route that only
returned the presigned URL would satisfy "same response shape" on paper and
store a blog cover that breaks the same afternoon — the exact failure the
tenant route's own comment describes. The durable path is /api/public/images/,
and its parser only served `tenants/{id}/uploads/`, so it had to learn one more
shape. That is why this story touched a shared module and not just the route.

Two alternatives rejected:
- Uploading under `tenants/platform/uploads/` to avoid touching the module. It
  works mechanically (the S3 scope guard would accept it), and that is the
  problem: a fabricated tenant id that satisfies a tenant guard by accident,
  written into every key, for the rest of the bucket's life.
- Returning publicUrl: null and letting US-007 deal with it. That pushes an
  expiring URL into the database, which is what the whole durable-image route
  exists to prevent.

Scope of the widening, checked rather than assumed: the platform prefix opens
`platform/uploads/` ONLY. The pre-existing platform branding keys written by
super-admin/platform-settings (`platform/logo-*`, `platform/favicon-*`) are
passed to uploadFile as a FILENAME with no prefix, so they land at
`{folderPrefix}uploads/{ts}-platform/logo-…` and match neither shape — they
stay private. Four negative tests pin that (`platform/logo-…`,
`platform/backups/…`, `platformX/uploads/…`, an SVG under the platform prefix).
PublicImageRequest.tenantId is now `string | null`; both call sites (the images
route, the OG card route) read only s3Key and contentType, so nothing broke.

WHY NOT /api/tenant-admin/upload (AC-2, verified in code)
It is withTenantAuth, which reads tenantId off the user and 403s when there is
none — a super-admin has none. Under impersonation it would succeed and file
the platform's blog cover inside a tenant's folder, where a tenant delete would
eventually take it. Also: getFileUrl is called WITHOUT the { tenantId } option
here, deliberately — that option asserts the key sits in that tenant's prefix
and would throw 403 on every platform upload. A test pins the bare call.

THE FOUR DECISIONS IN THE SQL, RE-VERIFIED AGAINST THE CODE
1. TIMESTAMPED DIRECTORY, not a loose .sql. Confirmed the seven loose files are

3. ON CONFLICT ("slug") DO NOTHING, never DO UPDATE. platform_posts_slug_key

4. publishedAt = the post's own date at 12:00 UTC, minus one minute per position

   lib/platform/published-posts.ts:66 orders by publishedAt DESC then createdAt
   DESC — identical stamps would order the pair arbitrarily between deploys.
   Midday keeps formatPostDate (date-fns, server-local zone) on the intended
   calendar day either side of UTC. Column is TIMESTAMP(3), so the bare literal
   is correct.
