WHAT LANDED
`lib/seo/ai-crawlers.ts` is the registry: nine user-agent tokens, each carrying
its class (search | training), owner and purpose. `lib/seo/robots-txt.ts` renders
the store's robots.txt from it. `app/store/[slug]/robots.txt/route.ts` now reads
the plan and the policy off the row `getCurrentTenant` already resolved — no
extra query — and a Pro-only `PUT /api/tenant-admin/seo/ai-crawlers` writes the
policy into `tenants.settings`. New "AI Crawlers" tab in the SEO Manager
(Pro-only), plus an `ai-crawlers` entry in `SEO_PRO_FEATURES` so a Basic tenant
meets the locked card.

THE ROBOTS.TXT RULE THAT SHAPED THE DESIGN. A crawler that matches its own
`User-agent` group uses THAT group and ignores the `*` group entirely (RFC 9309
§2.2.1). So a blocked bot gets its own group with `Disallow: /` (complete on its
own — the admin paths need no repeating), and an ALLOWED bot gets no group at
all. Publishing `User-agent: GPTBot` / `Allow: /` to "be explicit" would have
taken GPTBot out of the wildcard group and handed it `/api/`, `/tenant-admin/`
and `/auth/`. Hence 'open' renders comments and nothing functional — asserted
(`userAgents(txt)` is exactly `["*"]` under 'open').

TWO PARSERS, TWO DIRECTIONS, ON PURPOSE. The PLAN fails closed ('basic' — a DB
blip must not hand out Pro); the POLICY fails open ('open' — an unreadable
settings blob must never be read as "this store asked to be hidden from AI
answers"). Both directions are table-tested.

BYTE-IDENTICAL FOR BASIC. The pre-story file is frozen as a literal in the test
(not derived from the renderer, which would make the assertion tautological) and
asserted for plan 'basic' AND for every unreadable plan value, including a tenant
that stored 'blocked' while on Pro and then downgraded — the setting stays in the
column, dormant. The storefront never blocks on plan.

NO xAI ROW SHIPS — an evidenced deviation from the story's AC, stated here
rather than papered over. The AC asks for "xAI search UA". xAI publishes no
crawler user-agent token: x.ai's own robots.txt names other operators' bots and
not its own (curled 2026-08-14), and Cloudflare's AI Crawl Control bot reference
lists no xAI crawler. Third-party directories disagree with each other between
`GrokBot`, `xAI-Grok` and `xAI-Crawler`. Emitting a guessed token would tell an
owner they had blocked something they had not — the one failure this feature
cannot have. The registry is data; the row is one line the day xAI documents it.
Tokens that DID ship were verified against primary sources on 2026-08-14:
developers.openai.com/api/docs/bots, privacy.claude.com article 8896518,
docs.perplexity.ai/guides/bots, cross-checked against Cloudflare's bot reference.

COPY IS THE FEATURE, AND IT IS TESTED. Owners arrive believing "AI bots" is one
thing. Each class states what refusing it COSTS: blocking search = "absent from
AI answers"; blocking training = "does not remove you from AI answers today".
The policy note says plainly that robots.txt is "a published request, not a
lock" and that a crawler ignoring it is not stopped. User-triggered fetchers
(ChatGPT-User, Claude-User, Perplexity-User) are deliberately ABSENT from the
registry with a note saying why — their operators publish that robots.txt does
not apply to a request a person made directly, so listing them under a policy
switch would offer control this file does not have. No option summary may promise
a citation — asserted by regex.

SETTINGS KEY BOUNDED BY LENGTH, NOT BY ENUM — the `reorderReminderDays` /
verification-token split, for the documented reason: `parseTenantSettings` fails
as a UNIT, so an out-of-enum value hand-edited into the column would return `{}`
and take the tenant's tagline, colours and cookie banner down with it. The enum
is enforced by the write route on the way in (`z.enum` + `.strict()`) and
re-applied by `parseAiCrawlerPolicy` on the way out. Asserted.

GATES. `requirePermission("canEditSeo")` wrapping `requireFeature(SEO_PRO)`, the
sanctioned order — a member without the permission is refused BEFORE the plan
read (asserted: `tenants.findFirst` never called). Basic → 403 `upgrade_required`
and no write. The settings merge is read-modify-write over the RAW blob, so keys
this platform version has never heard of survive (asserted). Audit row

[2026-08-14] US-002 PASS — Product Q&A blocks
================================================================================

WHAT LANDED
`products.seo.qa` — a key in the authored Json record every other SEO field
already shares, so no migration. `lib/seo/product-qa.ts` is the storage contract
(limits + the fail-closed reader + `hasQaField`); `entity-seo.ts` gained the
key and a THIRD write half; the product SEO PUT validates it with Zod and gates
it with `featureDenial`; the product page renders it twice — a `<details>`
accordion for a person and a `FAQPage` node for a machine — from ONE gated read.
Drafting is a sibling route, `POST /api/tenant-admin/seo/ai-assist/qa`, on the
same service, the same meter and the same credentials as US-025's field
assistant, with a NEW output contract in `lib/seo/qa-draft.ts`.

THE ACCORDION IS A SERVER COMPONENT, AND THAT IS THE WHOLE STORY. `ProductDetail
Client` fetches the strain in the BROWSER, so its first render — the one that is
server-rendered into the initial HTML — is the loading spinner (product-detail-
client.tsx:129-152). Anything placed inside it does not exist for a reader that
does not execute JavaScript, which is most of the answer engines this PRD is
aimed at, and the FAQPage node would then be describing content no crawler could
verify. So the block is a sibling of the client component, rendered by the route
from the `seo` the page ALREADY resolved (`loadProductForRender`, the cache()d
loaders `generateMetadata` shares) — no extra query. `<details>`/`<summary>`
rather than a button and a state hook: collapsible, keyboard-operable, screen-
reader-announced with no client JS, and the answer stays in the DOM while
collapsed, which is what makes it extractable. Asserted: the element tree
carries every question and every answer.

ONE GATED READ, TWO CONSUMERS. `productQaEntries(source)` applies the plan gate
and the parse; `buildProductQaJsonLd` calls it, and the page passes its result to
the section. Structured data is policed on MATCHING the visible content, so the
two must not be able to disagree about the plan, the parse, or which pairs
survived — routing both through one function makes that structural. Asserted:
with junk mixed into the stored list, the node's questions equal
`productQaEntries`' questions exactly.

DEVIATION FROM THE AC, STATED: the accordion is NOT `bs-*`. Those component
classes are the ADMIN design system — dark card/gold/green tokens, applied under
the `[data-surface="admin"]` gate (app/globals.css:1262-1268, 1377+) — and
`grep -r "bs-card\|bs-btn\|bs-chip" app/store` returns NOTHING: no storefront
page uses one. The section is themed the way every other block on the product
page is, through the tenant's own `--tenant-color-*` variables, so a store's Q&A
looks like the store rather than like the admin panel dropped into it.

A THIRD WRITE HALF, NOT A THIRD MEANING FOR THE EXISTING FLAG. Q&A is authored
for a READER (like title/description) but Pro-gated (like the crawler
directives), and the two preserve decisions are genuinely independent: a Pro
tenant editing only Q&A must not have their indexing rules rewritten from a body
that never mentioned them, and vice versa. `entitySeoWrite` now composes
content + indexing + qa from explicitly-named sources instead of "submitted,
unless…" — the old shortcut return would have carried one group's submission
into a save that was refused it. All four flag combinations are asserted, plus
the no-options call, which behaves exactly as it did before.

FAQPage HAS ONE BUILDER NOW. US-017's condition FAQ and this both emit the same
node about a different page, so `buildFaqPageNode(url, entries)` was extracted
from `buildConditionFaqJsonLd` and both call it. The gate and the column stay
the caller's business. `readFaqEntries` was deliberately NOT reused for the
product parse: it is zod-based, and `entity-seo.ts` states in its own docstring
that it carries no zod because a client component imports it — so
`lib/seo/product-qa.ts` is hand-rolled and dependency-free, and the SHAPE is
asserted in both directions instead (the route's zod schema in, the parser out),
which is the arrangement `isCanonicalOverrideUrl` already has.

THE AI CONTRACT REFUSES A LIST THE WAY US-024 REFUSES A SENTENCE. `{"text": …}`
cannot express a list, so `parseQaDraft` demands a JSON array of pairs and
judges one: shape, then content, then the limits, measured after whitespace
normalisation. A violation refuses the WHOLE draft rather than dropping the two
bad pairs of eleven — a quietly shortened list is one the owner saves believing
a human wrote every line. Refusal reasons are their own union (`too_many`,
`question_too_long`, …) because the parent's "74 characters, over the 60 limit"
wording says nothing useful about a list. The prompt bans invented medical,
potency, price and availability claims and tells the model to LEAVE A QUESTION
OUT rather than fill it in — a Q&A block is read as the store answering, and an
invented claim would be published in the owner's name and quoted back as theirs.

THE PIPELINE WAS FACTORED, NOT COPIED. `runCompletion` (meter -> credentials ->
provider) is now shared by `generateSeoDraft` and `generateQaDraft`, so adding
this contract added an output PARSER and nothing else: one place still decides
how a tenant's AI quota is spent. The two share ONE rate-limit budget on purpose
— it is one AI account either way (asserted on the limiter key). The non-draft
HTTP shapes moved to `lib/seo/ai-assist-http.ts` because a Next route file may
only export handlers, so the second route could not import the first's mapping;
two copies would have drifted on a status code clients branch on.

GATES. `requirePermission("canEditSeo")` wrapping `requireFeature(SEO_PRO)` on
the draft route; permission-then-plan on the PUT, so a member without the
permission is refused BEFORE the plan read (asserted: `tenants.findFirst` never
called). A Basic tenant sending `qa` gets 403 `upgrade_required` and no write —
INCLUDING `qa: []`, because clearing the last question is a Pro write and a gate
that only noticed non-empty lists would let Basic undo a Pro configuration. One
plan lookup covers both Pro groups, and a Basic tenant saving only a title still
pays none. Storefront never blocks: Basic renders no accordion and no node, and
their pairs stay in the column, dormant.

COPY IS HONEST, AS THE RUN REQUIRES. The editor says the pairs render on the
page and as FAQ structured data, "the form search and AI answer engines read" —
and then, in the same paragraph, "it is not a guarantee of being cited". No
string in this story promises a citation or a ranking.
