US-003 — Concurrency unit proof (node-only AC-7)                       [DONE]
--------------------------------------------------------------------------------
tests/unit/tenant-context.concurrency.test.ts (4 tests, pure ALS — no DB):
  POSITIVE PROOF (the AC-7 property): 300 interleaved requests round-robin
  across 3 tenants, each yielding the microtask queue 5x and re-asserting its
  bound context after every yield (1500 interleaved observations) → ZERO
  cross-tenant observation; every request ends on its own tenant; context fully
  torn down after.
  ROOT-CAUSE CONTRAST (deterministic, not timing-dependent):
    (a) enterWith() with no enclosing scope persists into the shared context —
        after request1 finishes, a later read still sees 'req1' (never popped) —
        the exact bleed vector on Railway's persistent process.
    (b) enterWith() overrides an active run() scope in place (honours no
        boundary) — the enclosing 'outer' becomes 'intruder'.
    (c) runWithTenantContext() confines its binding — caller is null before and
        after; one request's binding cannot escape into another's continuation.
NOTE: I first tried a literal interleaved-enterWith bleed assertion; it did NOT
reproduce reliably on Node 18.17 because each `await` snapshots the context
frame. Rather than ship a flaky/contrived assertion, the contrast now proves the
underlying no-boundary mechanism deterministically. The authoritative full-stack
red→green interleave proof remains the Docker-gated Postgres test US-010.
Validation: full pnpm test:unit → 14/14 passed (3 files). tsc --noEmit → 0.

US-005 — Harden Prisma middleware: fail loud on implicit-unbound (AC-6/AC-6a) [DONE]
--------------------------------------------------------------------------------
lib/tenant-scope-policy.ts (new, pure policy — imports only tenant-context, no cycle):
  - class TenantContextMissingError extends Error: carries readonly model/action,
    name = "TenantContextMissingError", actionable message (wrap the boundary /
    use bypassTenantScope).
  - contextFreeAllowList = new Set<string>([]) — OQ-2 default-DENY (empty). A model
    earns a slot here only with a reviewed justification, never to silence a
    not-yet-wrapped route (those keep working via warn-not-throw).
  - isStrictTenantContext(env = process.env): env.TENANT_CONTEXT_STRICT === "true".
    Injectable env map so it is testable without mutating process.env; exact-string
    match (so "1"/"TRUE"/"false" are all OFF). Default OFF in prod (OQ-3 migration
    window) — flipped ON once PRD-203's withTenantAuth has wrapped the routes.
  - decideMissingContext({model,bound,strict,allowList?}) -> "allow"|"warn"|"throw":
    PURE. bound -> "allow" (explicit-null system query, the AC-6a distinction);
    else allowList.has(model) -> "allow"; else strict ? "throw" : "warn".
  - emitTenantContextMissing(model,action): console.warn("security.tenant_context_
    missing", JSON{event,model,action}) — sanctioned audit channel (warn, not log).
  - bypassTenantScope<T>(fn): runWithTenantContext(null, fn) — explicit-null binding
    for deliberate system queries; works sync & async (ALS .run propagates).
lib/db.ts middleware rewired (the hardening): the old early-return
  `if (!tenantId || !model || !scoped) return next()` CONFLATED three cases and let
  a tenant-scoped query on an UNBOUND context silently run unscoped (the leak). Now:
  (1) not-scoped model -> next(params) unchanged; (2) scoped + tenantId null ->
  decideMissingContext(bound = hasTenantContext(), strict = isStrictTenantContext());
  emit on warn|throw; THROW TenantContextMissingError when "throw"; else next()
  unscoped (explicit-null system query, allow-listed, or migration-window warn);
  (3) tenantId present -> existing scoping logic byte-for-byte unchanged.
  Guarded by `if ('$use' in prisma)` so the build-time mock client is untouched.
tests/unit/tenant-scope-policy.test.ts (11 tests, pure — no DB): full allow/warn/
  throw matrix incl. bound-beats-strict and injected allow-list; isStrictTenantContext
  exact-string flag reading; error is an Error subclass carrying model/action+name;
  emit calls console.warn once with the parsed JSON payload (spy); bypassTenantScope
  binds explicit null (hasTenantContext true / id null inside, torn down after) for
  both sync and async fn (context survives an await).
NOTE: strict-mode is default OFF, so not-yet-wrapped routes WARN (don't break) during
  the PRD-203 migration; the authoritative real-DB proof that the middleware actually
  throws under Postgres is the Docker-gated US-011.

>>> RISK FLAG FOR HUMAN REVIEW (migration-window behavior, by design but worth eyes):
Before this story, every getCurrentTenant/getTenantFromRequest call bound context as
an enterWith side-effect. The ~96 routes + tenant-scoped Server Components that are
NOT yet wrapped (everything except the two pilots US-006/007) therefore lose their
implicit binding here. With TENANT_CONTEXT_STRICT OFF (the prod default, OQ-3), the
US-005 middleware now WARNs (security.tenant_context_missing) and runs such a query
UNSCOPED rather than throwing. For queries that already pass an explicit
`where: { tenantId }` (the prevalent pattern in every route I read — orders,
orders/customer, consultation/status, conditions) this is harmless: the explicit
filter still scopes them and the middleware is belt-and-suspenders. For any
tenant-scoped query that relied SOLELY on the middleware (no explicit tenantId) this
is a transient cross-tenant exposure until PRD-203 wraps the route. Mitigations, in
order of safety: (a) set TENANT_CONTEXT_STRICT=true to fail CLOSED (throw, no leak)
once enough routes are wrapped; (b) monitor the warn events; (c) PRD-203 withTenantAuth
wraps the remaining routes. This is the exact trade-off the PRD designed the flag for,
but a full audit of middleware-only-scoped queries is PRD-203's job, not this PRD's.
Recommend Gerard confirm the strict-flag rollout plan before/with the PRD-203 merge.
