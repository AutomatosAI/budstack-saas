DONE — US-003 — Harden auth wrappers to bind tenant context (AC-1b) — 2026-05-30
================================================================================
Change (lib/api-auth.ts): the 5 wrappers previously did the role check only and
called handler() in the bare request scope (no tenant context). Each now runs the
handler INSIDE PRD-202's runWithTenantContextAsync, so the lib/db.ts middleware
sees an explicit, confined scope:
  - withTenantAuth / withTenantAuthParams -> runWithTenantContextAsync(tenantId,…)
    (the user's own tenant, already asserted non-null by the 403 check).
  - withSuperAdmin / withSuperAdminParams -> runWithTenantContextAsync(null,…)

    stays true, so the middleware does NOT treat it as the unbound-leak bug).
  - withAuth -> resolves the HOST tenant via getTenantFromRequest(req) and runs
    runWithTenantContextAsync(hostTenant?.id ?? null, …). This is what will scope
    customer/profile (US-005) to the storefront tenant.

and DROPPED Next's { params }. It now takes RouteHandlerWithParams<AuthContext>,
accepts the optional route context, and forwards params (defaulting to {}) as the
handler's 3rd arg — so param'd any-auth routes (store/[slug]/**, tenant/[slug])
won't break on migration. withAuth had ZERO call sites today, so the signature
change breaks nothing; the 5-wrapper count (and the US-002 gate's APPROVED_WRAPPERS
list) is preserved — no withAuthParams added.

Imports added: getTenantFromRequest (@/lib/tenant), runWithTenantContextAsync
(@/lib/tenant-context). Role-check 401/403 short-circuits are unchanged and stay
OUTSIDE the binding (they never touch tenant-scoped models). getCurrentUser still
runs BEFORE binding (it resolves WHO the user is, incl. tenantId — cannot itself
be tenant-scoped; US-004 hardens it). No route bodies changed (AC-1b).

Change (lib/auth-helper.ts): getCurrentUser now consumes 205's canonical resolver
DIRECTLY (resolveTenant({kind:'clerk',clerkOrgId,email})) instead of the old
resolveTenantIdFromClerkOrg delegator. The delegator collapses BOTH "ambiguous"
and "not-found" into null — it cannot surface the ambiguity signal AC-2 needs.
Calling resolveTenant directly lets getCurrentUser branch on the typed result:
  - isAmbiguousTenantResolution(resolved) -> throw AmbiguousTenantError (403).
    Email maps to >1 ACTIVE tenant; we refuse to authenticate against an
    arbitrary tenant. Resolver already emitted tenant.resolution_ambiguous; the
    email/candidate count stay in its audit log, never the 403 body (generic msg).
  - resolved?.tenantId ?? null otherwise.

Two typed ApiError subclasses added (so the wrappers' existing catch -> apiError
maps them to status + safe message, no stack leak):
  - AmbiguousTenantError  extends ApiError(403) — "could not be matched to a
    single organization."
  - UserNotProvisionedError extends ApiError(409) — "still being set up. Please
    retry." The user.created RACE (AC-2a): a valid Clerk session can arrive before
    the webhook writes the users row (keyed by EMAIL — app/api/webhooks/clerk).
    Probe is GUARDED to the hot-path-cheap case: only when tenantId == null && email
    (a resolved tenant already implies a provisioned row -> no extra query; no email
    -> nothing to key on). No row -> 409 retryable + console.warn audit
    (auth.user_not_provisioned, clerkUserId only, NO PII), never a silent null the
    wrappers would misreport as 401/403.

currentUser() try/catch retained: an expired/malformed Clerk token throws ->
caught -> return null (clean 401 via the wrappers), not a caught 500. Return shape
UNCHANGED (7 keys: id,email,name,image,role,tenantId,clerkOrgId) so api-auth.ts's
AuthUser type is unaffected and the wrapper/migration work rides on top untouched.
resolve-tenant-id.ts left in place (still used elsewhere; has its own test) — only
getCurrentUser stopped importing it.
